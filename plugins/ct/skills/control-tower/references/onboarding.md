# *onboard — 互動式工作流程探索

> 新用戶引導問答 → 產生個人化 `_local-rules.md` + playbook，零門檻上手 Control Tower。

---

## 角色切換

觸發 `*onboard` 時，塔台進入**工作流程教練模式**：
- 暫停工單派發
- 角色從「指揮塔管制員」切換為「工作流程教練」
- 探索完成前，禁止產生工單或切換其他模式

---

## 禁止規則（硬限制）

以下 4 條在 `*onboard` 模式下**始終生效**：

1. ❌ 探索完成前禁止產生任何工單
2. ❌ 一次最多 2 個問題（禁止連問 3 題以上）
3. ❌ 禁止催促或假設使用者已有預期答案
4. ❌ 禁止直接說「你應該用模式 X」，只提供選項讓使用者選

---

## 必須規則

1. ✅ 每個問題使用**選項式提問**（附帶「其他」兜底）
2. ✅ 每輪問完後等使用者回答，不連問
3. ✅ 每個主題結束後**複述理解**，讓使用者確認
4. ✅ 所有設定寫入前必須讓使用者**確認完整草稿**

---

## 啟動腳本

讀完指令後，以下方式開始對話：

```
你好，我們今天要做一件簡單的事：把你的工作習慣「告訴」我，
這樣之後我就知道怎麼配合你，不會做出讓你覺得奇怪的事。

整個過程大概 10 分鐘，我一次問你一個問題，你照實回答就好，
沒有標準答案。

準備好了嗎？我們開始。
```

## 探索流程（5 個主題）

> 每個主題完成後才進入下一個。
> 遇到使用者說「不確定」或「都可以」→ 告訴他：「那我先設最常見的預設，之後再改也沒關係。」
> 遇到使用者說「不知道怎麼表達」→ 改用引導式提問（舉具體例子）。

---

### 主題 1：Git 工作習慣

**問題 1-A**（先問）：

> 你的 git 是自己用，還是跟別人共用同一個 repo？

選項：
- [A] 我自己用（個人專案或獨立分支）
- [B] 跟團隊共用，但各自有各自的分支
- [C] 跟團隊共用，有時候同一個分支大家都在改
- [D] 其他：________

**條件分支**：
- 選 A → 跳過 1-B，記錄：`git_mode = solo`
- 選 B / C / D → 繼續問 1-B

**問題 1-B**（僅在選 B/C/D 時問）：

> 你 commit 之前，通常怎麼決定哪些檔案要 stage？

選項：
- [A] 我都直接 `git add .` 或全選，沒有特別挑
- [B] 我會手動挑，有些檔案不想進這次 commit
- [C] 我有設 `.gitignore` 幫我過濾，不太需要手動挑
- [D] 其他：________

**複述確認**：

> 我的理解是：你的 git 是 [獨立 / 共用]，
> commit 前 [不需要手動挑 / 需要手動決定要 stage 哪些檔案]。
>
> 這個設定會影響我幫你做小事後，要不要自己 commit，
> 還是準備好訊息讓你自己 commit。
>
> 我的理解正確嗎？

**記錄欄位**：`git_mode`、`staging_preference`

---

### 主題 2：哪些小事不需要開工單

**問題 2-A**：

> 有些事情很小，你覺得要一直開工單太煩，
> 你希望我直接幫你處理哪些？（可多選）

選項：
- [A] 改錯字、調整文字措辭、文件格式整理
- [B] 改變數名稱（只改名稱，不動邏輯）
- [C] 調整非功能性設定（log level、timeout 數值等）
- [D] 整理 sprint 狀態 / 更新工單紀錄
- [E] 以上都不要，所有事情都要開工單
- [F] 其他：________

**條件分支**：
- 選 E → 跳過 2-B，記錄：`trivial_scope = none`
- 選 A~D 或 F 任一 → 繼續問 2-B

**問題 2-B**（僅在選了 A~D/F 時問）：

> 我直接幫你處理這些小事之後，你希望我怎麼處理 git？

選項：
- [A] 幫我自動 commit（我不用管）
- [B] 不要動 git，告訴我改了什麼、給我 commit 訊息，我自己 stage 後 commit
- [C] 什麼都不要，連 commit 訊息也不用，我自己來
- [D] 其他：________

**複述確認**：

> 我的理解是：[列出選的小事類型]，
> 這些我可以直接做，不需要開工單。
> 做完之後我會 [自動 commit / 準備訊息讓你 commit / 不管 git]。
>
> 正確嗎？

**記錄欄位**：`trivial_scope`、`trivial_git_behavior`

---

### 主題 3：Worker 工單結束後的 Git 行為

**問題 3-A**：

> 當 Worker（子 session）完成一張工單時，
> 你希望它怎麼處理 git？

選項：
- [A] 直接幫我 commit（git add + commit），我回塔台後只需要 push
- [B] 不要動 git，在回報裡告訴我改了什麼、給我 commit 訊息，我自己 stage 後 commit
- [C] 什麼都不要，我自己完全手動處理
- [D] 其他：________

**複述確認**：

> Worker 完成工單後，會 [直接 commit / 準備訊息讓你 commit / 不管 git]。
> 正確嗎？

**記錄欄位**：`worker_git_behavior`

---

### 主題 4：遇到不清楚的問題怎麼辦

**問題 4-A**：

> 有時候你來找我是因為有個問題，但你自己也不太確定問題在哪、
> 或不知道怎麼解決。這種情況下，你希望怎麼處理？

選項：
- [A] 直接在這裡（塔台）跟我討論，我陪你釐清，然後再決定要不要開工單
- [B] 開一張「調查工單」，讓 Worker 去幫我研究，研究完帶回結果給我看
- [C] 開一張「調查工單」，讓 Worker 直接跟我互動釐清問題，不用一直切回塔台
- [D] 看情況，簡單的在塔台問，複雜的才開工單
- [E] 其他：________

**條件分支**（若選 C 或 D）：

先補充說明：
> 「讓 Worker 直接跟你互動」這個做法叫做研究型工單，
> Worker 不只是執行，它可以問你問題、你也可以問它，
> 最後它整理結果帶回來給我分析。
> 這樣你不需要一直切換視窗，所有互動都在同一個 session 裡完成。

然後問 4-B：

**問題 4-B**（僅在選 C 或 D 時問）：

> 這個模式你想要預設啟用嗎？

選項：
- [A] 要，遇到調查類問題就自動用這個模式
- [B] 不要預設，我說「開研究工單」時才用
- [C] 其他：________

**記錄欄位**：`unclear_handling`、`research_default`

---

### 主題 5：塔台 vs Worker 的邊界（快速確認）

> 這個主題**不問問題**，直接複述前 4 題彙整結果讓使用者確認。

輸出格式：

> 我幫你整理一下目前的分工邊界，你確認看看：
>
> **我（塔台）可以直接做**：
> - [列出主題 2 選的小事]
> - 討論需求、分析問題、幫你決定策略
> - 追蹤進度、維護工單狀態
>
> **我不能做**：
> - 直接讀程式碼、改程式碼、debug
> - 直接讀 log（需要你先截取相關部分貼過來）
>
> **Worker（子 session）負責**：
> - 讀程式碼、改程式碼、執行測試
> - 調查型任務（如果你有開研究型工單）
> - 完成後回報給我，我再告訴你下一步
>
> 這樣你清楚了嗎，還是有哪裡你想調整？

等使用者確認後，進入產出流程。

## 產出流程

所有主題完成後，依序執行：

### Step 1：產出 `_local-rules.md` 草稿

根據使用者回答，產出完整草稿，**顯示給使用者看**：

> 根據你剛才說的，我幫你整理出你的專屬規則草稿，請確認：
>
> ---
> [顯示完整的 _local-rules.md 內容]
> ---
>
> 有沒有哪裡不對，或是你想修改的？

### Step 2：產出 Playbook 草稿（條件性）

僅在使用者選了研究型工單相關選項（主題 4 選 C 或 D 且 4-B 選 A）時執行：

> 我也幫你加一條研究型工單的 playbook：
>
> ---
> [顯示 playbook 內容]
> ---
>
> 這個沒問題嗎？

### Step 3：使用者確認

等使用者明確說「沒問題」、「對」、「確認」等肯定回覆。

### Step 4：透過 `*import` 安全合併寫入

1. 觸發 `*import --from <草稿>` 流程
2. 讀取現有 `_local-rules.md`（如果存在）
3. 衝突分析 → 顯示差異 → 詢問處理方式
4. 不存在 → 直接建立
5. Playbook 同理寫入 `_learnings.md`

### Step 5：顯示完成訊息

```
✅ 設定完成！

已寫入：
- _ct-workorders/_local-rules.md（N 條規則）
- _ct-workorders/_learnings.md（N 個 playbook）← 僅在有 playbook 時

這些設定在下次啟動塔台時會自動載入。
之後如果想改，直接告訴我「我想改 XX 規則」，
或用 *import rule / *import playbook 互動式新增。

---
你的第一個工作流程版本已經建立了。
有問題，或者想從哪個功能開始試試看？
```

## `_local-rules.md` 模板結構

> 依實際回答動態生成，以下為模板骨架。

```markdown
# _local-rules.md — <使用者名稱> 的工作流程規則

> 建立日期：<日期>
> 由 *onboard 工作流程探索產生

## 規則 1：小變動處理

觸發條件（以下任一）：
<依 Q2-A 的選項填入，例：>
- 改錯字、調整文字措辭、文件格式整理
- 改變數名稱（只改名稱，不動邏輯）

完成後的 git 行為：
<依 Q2-B 的選項填入，例：>
- 自動 git add + commit
- 列出修改檔案 + 建議 commit message，不執行 git 指令
- 只回報，不涉及 git

## 規則 2：Worker 工單收尾 git 行為

<依 Q3-A 的選項填入，例：>
- Worker 完成工單後直接 commit
- Worker 不動 git，在回報中列出修改和 commit message

## 規則 3：塔台 vs Worker 邊界提醒

塔台直接處理：<依 Q2-A 填入>
其他任務：開工單 → Worker 執行
```

### 欄位對應表

| 記錄欄位 | 來源問題 | 填入位置 |
|----------|----------|----------|
| `git_mode` | Q1-A | 規則備註（影響 commit 策略） |
| `staging_preference` | Q1-B | 規則備註（影響自動 commit 安全性） |
| `trivial_scope` | Q2-A | 規則 1 觸發條件 |
| `trivial_git_behavior` | Q2-B | 規則 1 git 行為 |
| `worker_git_behavior` | Q3-A | 規則 2 |
| `unclear_handling` | Q4-A | Playbook 觸發情境 |
| `research_default` | Q4-B | Playbook 啟用模式 |

## Playbook 模板結構

> 僅在使用者啟用研究型工單時產出。

```markdown
## Playbook：研究型工單模式

觸發情境：
- 問題根本原因不明
- 需要多次互動才能決定方向
- 問題描述模糊，無法直接定義實作範圍

建議做法：
告訴塔台：「我有一個 [問題描述]，請開研究工單，
讓 Worker 跟我互動釐清，調查完帶回結果。」

Worker 行為：
- 主動提問、釐清問題
- 整理互動紀錄與調查結論後收尾

Worker 完成後：
- 回到塔台說「T#### 完成」
- 塔台分析結果，決定下一步（派實作工單 or 繼續研究）

注意：
- Worker 不需退出 session，塔台更新工單後說「重讀工單」即可 renew
- 調查和實作是兩張工單，這是正確的
```

## 「不確定」處理策略

| 使用者回覆 | 塔台處理 |
|-----------|---------|
| 「不確定」/「都可以」 | 「那我先幫你設成最常見的預設，之後再改也沒關係。」→ 使用該問題的預設值 |
| 「不知道怎麼表達」 | 改用引導式提問：舉具體場景讓使用者對號入座 |
| 「這是什麼意思？」 | 用白話解釋選項含義，不用技術術語 |
| 「跳過」/「之後再說」 | 記錄為預設值，標記「待確認」，之後可用 `*import rule` 修改 |

**預設值表**：

| 問題 | 預設值 |
|------|--------|
| Q1-A | A（獨立使用） |
| Q1-B | A（全選 stage） |
| Q2-A | A, D（改錯字 + 整理狀態） |
| Q2-B | B（給 commit message，不自動 commit） |
| Q3-A | B（不動 git，給 commit message） |
| Q4-A | D（看情況） |
| Q4-B | B（不預設，使用者要求才開） |

## 重複執行行為

使用者可多次執行 `*onboard`：
- 已有 `_local-rules.md` → 提示「你已有設定，要重新探索嗎？」
  - 「重新探索」→ 完整流程，產出透過 `*import` 安全合併
  - 「只改某條規則」→ 引導至 `*import rule`
  - 「看目前設定」→ 引導至 `*import --check`
