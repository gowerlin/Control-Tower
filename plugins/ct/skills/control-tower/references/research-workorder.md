# 研究型工單系統

> 支援根因不明、需多輪互動才能決策的場景。Worker 可在 sub-session 中主動提問，收尾時自動整理互動紀錄和可決策結論。

## 觸發條件

塔台判斷以下情境時，**主動建議開研究工單**：

| # | 情境 | 使用者話術範例 | 塔台建議語 |
|---|------|-------------|-----------|
| 1 | 根因不明 | 「不確定問題出在哪」 | 「這個問題根因不確定，建議先開研究工單調查。」 |
| 2 | 需要多輪互動 | 「需要 Worker 跟我確認幾個方向」 | 「需要互動釐清方向，建議開研究工單讓 Worker 和你對話。」 |
| 3 | 方向不確定 | 「先調查再決定做法」 | 「技術方向待定，建議先開研究工單評估選項。」 |
| 4 | 問題描述模糊 | 「這個功能怪怪的」 | 「問題還不夠具體，建議開研究工單先調查範圍。」 |

**使用者主動觸發話術**：
```
「開一張研究工單，允許 Worker 與我互動釐清問題」
「這個問題根因不明，開研究單讓 Worker 調查」
```

## Worker 行為規格（research 類型專屬）

### 研究模式偵測

ct-exec Worker 讀取工單元資料時，偵測以下條件進入研究模式：

```
條件：「類型」欄位為 research AND「互動模式」欄位為 enabled
結果：啟用研究模式行為
```

互動許可以 runtime `CT_INTERACTIVE` 為優先（`1` 允許、`0` 禁止；未設才依工單元資料）。config `research_interaction` 是**塔台派工時**決定傳 `--interactive`／`--no-interactive` 的輸入，Worker 不讀 config 決定互動（D062）。權威定義見 [auto-session.md](auto-session.md) § Mode 與互動旗標協定、`ct-exec/SKILL.md` § Mode And Environment，本節不複述。

### 研究模式行為

| 行為 | 標準工單 | 研究型工單 |
|------|---------|-----------|
| 主動向使用者提問 | 禁止（只執行不提問） | **允許**（主動縮小範圍） |
| 提問策略 | N/A | 逐步縮小：大方向 → 小細節 |
| 每次提問上限 | N/A | `research_max_questions`（有效值與預設見 [tower-config.md](tower-config.md) § 可用選項） |
| 提問格式 | N/A | 選項式 + 「其他：________」兜底 |
| 互動紀錄 | 僅記錄使用者主動互動 | **必須**記錄所有問答（時間 + 問題 + 回覆 + 行動） |
| 回報區結構 | 產出摘要 + 遭遇問題 | 互動紀錄 + **調查結論** + **建議方向**（帶選項和推薦） |
| 結論要求 | 完成/未完成 | 必須是「可決策的」（例如「建議方案 A 因為 X」） |

**yolo 例外（v5.5.0+）**：`CT_MODE=yolo` 時，研究型工單的提問也不問使用者，改問塔台、由塔台代決（格式、等待與備援見
[yolo-mode.md](yolo-mode.md) § Worker 向塔台提問）；提問策略、每輪上限與互動紀錄格式照本節。非 yolo 不變。

### 提問策略

Worker 在研究模式下的提問遵循「漸進收窄」原則：

```
第 1 輪：大方向確認
  → 確認問題範圍、影響模組、使用者預期

第 2 輪：技術細節
  → 確認技術限制、效能需求、相容性要求

第 3+ 輪：方案確認
  → 提出候選方案，請使用者確認偏好或補充
```

**提問格式要求**：
- 每個問題提供 AI 預判的選項（參考塔台 `interactive-prompts` 機制）
- 最後一項為自由輸入兜底：「其他：________」
- 一次最多問 `research_max_questions` 個問題
- 問題之間有邏輯遞進關係，不重複已知資訊

### 互動紀錄格式

所有 Worker 與使用者的問答**必須**記錄到回報區「互動紀錄」：

```
[HH:MM] Q: <問題摘要> → A: <使用者回覆> → Action: <採取的行動>
```

範例：
```
[14:05] Q: 問題發生在哪個模組？[A]前端 [B]後端 [C]API 層 → A: B（後端） → Action: 聚焦 service 層調查
[14:12] Q: 後端哪個 service 最可疑？[A]AuthService [B]OrderService [C]不確定 → A: A → Action: 深入 AuthService 追蹤
[14:20] Q: JWT token 過期處理是否有自訂邏輯？ → A: 有，在 middleware 中 → Action: 比對 middleware 和標準做法差異
```

### 結論品質要求

研究型工單的「調查結論」**必須是可決策的**，不只是調查日誌。

**合格結論範例**：
```
根因：AuthService 中的 JWT refresh 邏輯使用了 synchronous blocking call，
在高並發時導致 thread pool exhaustion。

建議方案：
[A] 改為 async refresh：改動小，但需要升級 auth library 到 v3+
[B] 加 circuit breaker：不改 refresh 邏輯，加防護層，影響範圍小
[C] token 延長有效期：最簡單，但安全性降低

推薦：方案 A，因為 auth library v3 已在路線圖中，順便解決技術債。
```

**不合格結論範例**：
```
我查了 AuthService 的程式碼，發現了一些可能的問題。
JWT 相關的 function 有好幾個，需要進一步研究。
```

## 塔台決策流程

塔台收到研究型工單回報後的決策流程：

```
收到研究工單回報
  → 結論是否清晰可決策？
     ├─ 是 → 問題解決了？
     │       ├─ 是 → 標記 DONE，記錄結論到決策日誌
     │       └─ 否 → 基於研究結論派發實作工單（T####）
     │              └─ 實作工單引用研究工單：「基於 T<研究工單編號> 結論，方案 X」
     └─ 否 → Renew 同一張工單（見 F-07 Renew 機制）
              └─ 塔台新增「塔台補充（Renew #N）」區段
              └─ Renew 次數 +1
              └─ 補充新的調查方向或修正範圍
```

### 實作工單引用研究結論

從研究工單衍生實作工單時，在「輸入上下文」區段引用：

```markdown
### 輸入上下文

**決策依據**：基於研究工單 T0045 結論（方案 A：async refresh）。
研究工單互動紀錄確認：使用者同意升級 auth library v3。

<其餘上下文...>
```

## Renew 機制（F-07）

> 當塔台更新工單補充新指示時，Worker 不需退出 session，重讀工單中新增的「塔台補充」區段即可繼續執行。

### 適用範圍

- **主要**：研究型工單（`type: research`）— 多輪調查是常態
- **也可用於**：一般工單（T####）— 使用者決定，無類型限制

### 塔台端：Renew 區段格式

塔台更新工單時，在工單回報區（`---` 分隔線）**之前**插入新區段：

```markdown
## 塔台補充（Renew #N）

**時間**：<datetime> (UTC+8)
**補充內容**：
> <塔台整理的新資訊或方向調整>

**新指示**：
> <具體的新執行指示>
```

**規則**：
- Renew 編號遞增（#1, #2, #3...），每個 Renew 獨立成區段
- 多次 Renew 時，新區段插在前一個 Renew 區段之後、回報區 `---` 之前
- 同時更新元資料中的 `Renew 次數` 欄位（+1）

### 塔台操作流程

1. 使用者回報研究結論不足或需要補充方向
2. 塔台判斷需要 Renew（而非開新工單）
3. 塔台編輯工單：
   - 在回報區 `---` 之前插入 `## 塔台補充（Renew #N）` 區段
   - 更新元資料 `Renew 次數`（+1）
4. 塔台告知使用者：「工單已更新，請回 sub-session 告訴 Worker：**重讀工單**」

使用者在原分頁「重讀工單」時不回收任何分頁：那個分頁就是要繼續的 Worker。塔台改為派新 Worker 重跑這張工單時（例：`BLOCKED`／`FAILED` 後重派、
yolo 提問備援），派工前先照 [work-order-system.md](work-order-system.md) § 回報處理流程 › 重派前回收舊 Worker 分頁（v5.12.0+）。

### Worker 端：Renew 偵測與行為

**觸發詞**（使用者在 sub-session 中說）：
- 「重讀工單」
- 「renew」
- 「塔台有新指示」
- 「工單已更新」

**Worker 收到觸發詞後的行為**：
1. 重新讀取工單檔案
2. 找到最新的 `## 塔台補充（Renew #N）` 區段（N 為最大編號）
3. **只讀取該 Renew 區段**（不重讀整張工單其他部分，保留已有上下文）
4. 向使用者確認：摘要補充內容和新指示
5. 根據新指示繼續執行（不重置已完成的工作）
6. 收尾時在回報區「Renew 歷程」標註每次 Renew 的摘要

### 回報區 Renew 歷程格式

```markdown
### Renew 歷程
- Renew #1（21:00）：塔台補充 Redis 連線調查方向 → 確認 ConnectTimeout 問題
- Renew #2（21:30）：塔台指示評估三個方案 → 推薦方案 B
```

若無 Renew 則填「無」。

### Renew vs 開新工單的判斷

| 情境 | 建議 |
|------|------|
| 方向微調、補充資訊 | Renew 同一張工單 |
| 需要完全不同的調查方向 | 開新工單 |
| Worker context window 接近上限 | 開新工單（帶前一張結論作為輸入） |
| 累計 Renew ≥3 次且無收斂趨勢 | 考慮開新工單重新聚焦 |

## 與其他功能的關係

| 功能 | 關係 |
|------|------|
| F-07 Renew | 研究結論不清晰時 Renew 同一張工單，是研究型工單的核心配套 |
| F-01 多文件類型引擎 | `*sync` 掃描時 research 類型工單按 T#### 前綴歸入 sprint 統計 |
| F-04 決策日誌 | 研究結論可記錄到 `_decision-log.md` 作為決策依據 |
| F-14 歷史封存 | 已完成的研究工單適用標準歸檔流程 |
