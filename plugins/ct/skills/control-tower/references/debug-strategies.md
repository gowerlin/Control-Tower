# Debug 策略與品質閘門

## Debug 三層防線

Sub-session 遇到問題時，依序建議：

### 第一層：TDD / ATDD（預防）

問題源於缺少測試？先寫測試定義預期行為，開發目標變成「紅→綠」。

- 適用：功能邏輯錯誤、邊界條件遺漏、併行資料干擾
- 產出：測試檔案，後續開發（`bmad-build`）以通過測試為目標

### 第二層：診斷腳本（自動化偵測）

派發「診斷工單」讓 sub-session 寫診斷腳本，使用者自己跑腳本後結果寫入工單回報區。

- 適用：錯誤難以重現、log 量大、需要統計分析
- 腳本類型：log parser、pattern detector、state checker、data validator
- 產出：精簡分析報告（目標：10000 行 log → 20 行結論）

### 第三層：結構化 log 分析（最後手段）

提供預處理指令讓使用者先過濾：
- 提供 grep / jq / awk 指令組合
- 過濾後上限 50 行
- **絕對不接受原始 log 直接貼入任何 AI session**

## 品質閘門

### 審查→修正→交付強制流程

當工單性質為「審查 / Review」且回報區包含 CRITICAL 或 HIGH 發現時：

1. **強制**派發修正工單，不可直接進入下一階段
2. 修正工單完成後，可選擇性派發覆核工單（原始 CRITICAL > 5 項時建議）
3. 進度表標記：審查 ✅ → 修正 🔄 → 下一階段

**來源**：CT000 實戰驗證——跳過修正步驟被使用者糾正。

### 交叉驗證原則

產出文件的 session 和審查文件的 session 必須分開，避免確認偏誤。
審查類工單的 Session 建議應為 🆕 新 Session。

## 工單失敗處理

| 回報狀態 | 塔台動作 |
|---------|---------|
| DONE | 正常流轉，進入下一張 |
| PARTIAL | 先判斷 blocker 是否已由後續工單、scope decision 或 final acceptance 解除；已解除則補 post-resolution note 並改為 DONE，未解除才產生接續工單或補充指引 |
| FAILED | 啟動 Debug 三層防線，可能派發診斷工單 |
| BLOCKED | 記錄卡點，評估可並行的其他工單 |
