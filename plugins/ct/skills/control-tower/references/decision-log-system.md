# 決策日誌系統

獨立的架構決策追溯系統，讓重要決策有完整紀錄，不再散落在 `_learnings.md` 或工單中。

## 檔案位置

`_ct-workorders/_decision-log.md`（手動維護，append-only；超過大小預算時照 § 收斂 把較舊的詳細紀錄移到封存檔）

收斂移出的詳細紀錄放 `_ct-workorders/_archive/decisions/_decision-log-D<起>-D<迄>.md`（§ 收斂）。

## 格式規格

```markdown
# Decision Log

## 索引

| ID | 日期 | 決策 | 相關工單 |
|----|------|------|---------|
| D002 | 2026-04-03 | API 改用 REST 而非 GraphQL | T0012 |
| D001 | 2026-04-01 | 選擇 React 而非 Vue | T0005 |

---

## 詳細紀錄（倒序）

### D002 2026-04-03 — API 改用 REST 而非 GraphQL

- **背景**：前端團隊較熟悉 REST，GraphQL 學習成本高
- **選項**：
  - [A] GraphQL：靈活查詢，但學習曲線陡
  - [B] REST：團隊熟悉，生態成熟
  - [C] tRPC：型別安全，但綁定 TypeScript
- **決定**：選 B（REST），理由：團隊生產力優先
- **影響**：API 層架構、前端 fetch 邏輯
- **相關工單**：T0012

### D001 2026-04-01 — 選擇 React 而非 Vue

- **背景**：<情境描述>
- **選項**：
  - [A] <選項 A>
  - [B] <選項 B>
- **決定**：選 A，理由：<理由>
- **影響**：<影響範圍>
- **相關工單**：T0005
```

### 格式規則

本節是 `_decision-log.md` 格式的**唯一權威定義**。第 1～4、6、7 條同時是 BAT 決策頁的讀法要求，
BAT 的讀法與對照版本見 [memory-protocol.md](memory-protocol.md) § BAT 塔台面板讀取契約。

1. **索引表**：表頭固定 `| ID | 日期 | 決策 | 相關工單 |`；倒序排列（最新在最上方），每條一行
2. **表格列**：每一列 trim 後以 `|` 開頭、以 `|` 結尾。儲存格內不得出現 `|`（含 `\|` 與行內 code 裡的 `|`），要分隔就用 `／`。
   缺列尾 `|` 的一列會讓 BAT 把表格截斷，後面的決策全部看不到
3. **索引表涵蓋熱檔裡的每一個決策**：熱檔有詳細紀錄的 D### 都要有索引列。BAT 只要索引表有任何一列就不看標題，漏列的決策在面板上看不到
4. **詳細紀錄**：倒序排列，每條為獨立區段，標題固定 `### D### YYYY-MM-DD — 標題`（例 `### D002 2026-04-03 — API 改用 REST 而非 GraphQL`）
5. **必填欄位**：背景、選項（至少 2 個）、決定（含理由）、影響、相關工單
6. **選項格式**：`[A]`、`[B]`、`[C]`... 字母標記，每個選項含簡要說明
7. **熱檔內不放其他含 `ID` 欄的表格**：BAT 會把任何有 `ID`（或 `編號`）欄的表格列當成決策。詳細紀錄裡需要表格時，欄名改用 `項`、`題` 之類
8. **索引與詳細紀錄一致**：索引表的 D### = 熱檔詳細紀錄 ∪ 封存檔詳細紀錄（§ 收斂），一筆不多、一筆不少（`*sync` 會驗證）

## 編號管理

### D### 編號規則

- 格式：`D` + 三位數字，從 `D001` 開始
- 遞增方式：每新增一條決策，編號 +1
- 編號永不重複、永不回收（即使刪除也不重用）

### `_tower-state.md` 追蹤

塔台在 `_tower-state.md` 中維護決策編號計數器：

```markdown
## 編號追蹤

- 工單最大編號：T0073
- 決策最大編號：D005
```

- 每次新增決策時，同步更新 `_tower-state.md` 中的 `決策最大編號`
- `*sync` 執行時，以 `_decision-log.md` 實際內容為準校正計數器
- 若 `_tower-state.md` 中尚無「編號追蹤」區段，塔台在首次記錄決策時自動補建

## 塔台操作流程

### 觸發方式

以下情境觸發決策日誌記錄：

1. **使用者主動**：使用者說「記錄一個決策」、「我們決定了...」或類似表述
2. **塔台建議**：塔台在討論中識別到重要架構決策，主動詢問「這個決策要記錄到決策日誌嗎？」

### 互動流程

```
1. 使用者描述決策情境
   ↓
2. 塔台以「選項分析」格式整理：
   - 自動擬定背景描述
   - 列出討論過的選項（含優缺點）
   - 標記最終決定和理由
   - 評估影響範圍
   - 關聯當前工單編號
   ↓
3. 塔台呈現格式化預覽，請使用者確認：
   「📝 決策紀錄預覽：
    D006 — [標題]
    背景：...
    選項：[A]... [B]...
    決定：選 A，理由：...
    影響：...
    相關工單：T0042

    ✅ 確認記錄？（可修改後再確認）」
   ↓
4. 使用者確認後，塔台執行：
   a. Append 到 `_decision-log.md`（詳細紀錄 + 索引表）
   b. 更新 `_tower-state.md` 編號追蹤
   c. 顯示確認：「✅ D006 已記錄到決策日誌。」
```

### 注意事項

- 塔台**不主動建立** `_decision-log.md`，僅在環境偵測時提示「🆕 可建立」
- 使用者確認建立後，塔台以空模板初始化（見下方「初始模板」）
- 決策日誌為 append-only，塔台不刪除或修改已有紀錄；唯一例外是 § 收斂：詳細紀錄**原文搬到封存檔**，不刪除、不改字

## 與 `*sync` 的關係

### 不重建

`*sync` **不重建** `_decision-log.md`。原因：

- 決策日誌無對應源文件群（不像 BUG/PLAN 有獨立單據檔案）
- 為 append-only 日誌，內容由人工維護

### 格式驗證

`*sync` 執行時對 `_decision-log.md` 進行格式一致性驗證：

1. **數量一致**：索引表行數 = 熱檔詳細紀錄區段數 + 封存檔詳細紀錄區段數（封存檔只用 `grep` 數 `### D###` 標題，不讀全文）
2. **編號一致**：索引表中的 D### 編號 = 熱檔與封存檔詳細紀錄標題中的 D### 編號；熱檔每一筆詳細紀錄都有索引列（§ 格式規則 第 3 條）
3. **排序正確**：索引表和詳細紀錄皆為倒序排列
4. **計數器校正**：以實際最大 D### 編號校正 `_tower-state.md` 中的計數器
5. **BAT 讀得到**：表頭是 `ID`；每列以 `|` 開頭與結尾；標題符合 § 格式規則 第 4 條；沒有其他含 `ID` 欄的表格
6. **大小**：依 [memory-protocol.md](memory-protocol.md) § BAT 塔台面板讀取契約 › 大小預算 量檔、輸出提示

驗證結果顯示在 `*sync` 報告中：

```
決策日誌：✅ 格式正確（5 條紀錄，最大 D005）
決策日誌：⚠️ 索引表有 5 條，但詳細紀錄有 4 條（缺少 D003）
決策日誌：⚠️ 索引表第 12 列缺列尾 `|`（BAT 會從這裡截斷）
決策日誌：⚠️ _decision-log.md 431,220 bytes，超過 400 KB 預算，建議收斂（decision-log-system.md § 收斂）
決策日誌：📋 未建立
```

## 收斂

`_decision-log.md` 超過大小預算（[memory-protocol.md](memory-protocol.md) § BAT 塔台面板讀取契約 › 大小預算）時，依本節把較舊的詳細紀錄移到封存檔。
塔台提示後由使用者決定何時做；塔台可以自己做，也可以開工單給 Worker（工單要寫明可改 `_decision-log.md` 與 `_archive/decisions/`）。
做的期間塔台不寫入 `_decision-log.md`，新決策先記在 `_tower-state.md`，收斂完再補寫。

1. **量大小**：記下收斂前的 bytes。
2. **選切點**：從最舊的決策往新的方向選一段連續範圍 `D<起>`～`D<迄>`，讓收斂後的熱檔大約在預算的一半以下（約 200 KB），留空間給之後的決策。
3. **搬移**：把範圍內每一筆詳細紀錄（`### D### …` 標題到下一個標題之前）**原文**搬到封存檔，不摘要、不改字。
   - 封存檔：`_ct-workorders/_archive/decisions/_decision-log-D<起>-D<迄>.md`（三位數補零，例 `_decision-log-D001-D250.md`；目錄沿用
     [archive-system.md](archive-system.md) § 歸檔目錄結構 的 `_archive/` 慣例，不存在就建立）。範圍不重疊，每次收斂一個新檔，不改舊封存檔。
   - 封存檔開頭兩行：`# Decision Log 封存（D<起>～D<迄>）`、`> 從 _decision-log.md 搬出，索引仍在熱檔。`；其後照原順序（倒序）放詳細紀錄，不放索引表。
   - **🔴 危害規則逐字留在熱檔**：詳細紀錄裡有標 🔴 的規則，或記錄危害（會造成資料遺失、誤刪、外洩、誤送的操作）與對應禁令的決策，不搬，整段原文留在熱檔。
     只是一般「不得」字樣的不算；拿不準就留。
4. **索引表不動**：熱檔的索引表保留**全部**決策（含已搬出的），BAT 決策清單才完整；搬出的決策在 BAT 展開時沒有詳情，這是預期的。
5. **加封存段**：熱檔在索引表之後加 `## 封存` 段，用條列（不用表格）寫每個封存檔的範圍與相對連結；已有就追加一條。
6. **驗證**：跑一次 § 與 `*sync` 的關係 › 格式驗證，並再量一次大小；收斂前後的 bytes、範圍與封存檔名記成一筆新決策。
7. **commit**：熱檔與封存檔放在同一個 commit。

## 初始模板

```markdown
# Decision Log

## 索引

| ID | 日期 | 決策 | 相關工單 |
|----|------|------|---------|

---

## 詳細紀錄（倒序）

（尚無紀錄）
```

## 環境偵測

偵測項加入 Step 0 環境偵測表：

| # | 偵測項 | 檢查方式 | 未偵測到時 |
|---|--------|---------|-----------|
| 14 | 決策日誌 | `test -f _ct-workorders/_decision-log.md` | 🆕 可建立 |

面板顯示：

```
║ 14. 決策日誌      ✅ D### (N 條) / 🆕 可建立                     ║
```

偵測邏輯：
- 檔案存在 → 讀取索引表計數，顯示「✅ D### (N 條)」
- 檔案不存在 → 顯示「🆕 可建立」，使用者確認後以初始模板建立
