# Sub-session 防護機制

> 在 `/ct-exec` 執行期間持續監控的防護規則。
> 目的：防止 sub-session 中的離題、死纏爛打、無限延伸等常見問題。
> 防護等級由 `experience-level` 設定決定。
> `CT_MODE=yolo` 時，下列各機制中向使用者提問的部分改依 § yolo 下的處理（v5.5.1+）；其他模式照本檔原文。

---

## yolo 下的處理（`CT_MODE=yolo`，v5.5.1+）

只在 `CT_MODE=yolo` 時適用；`CT_MODE` 為其他值或未設定時，本節不適用，下列四項機制完全照原文。
yolo Worker 不向使用者提問（[yolo-mode.md](../../control-tower/references/yolo-mode.md) § Worker 向塔台提問）。
觸發條件、計數方式、experience-level 差異不變，只改「問使用者」的那一步：

| 機制 | 原文問使用者的地方 | yolo 下 | 理由 |
|------|------------------|---------|------|
| 1. 範圍守衛 | `[A/B/C]` 選項 | 一律照 [B]：記到回報區，不擴大範圍。若不先決定就無法完成工單，改向塔台提問（範圍變更屬塔台代決邊界外，塔台會轉問使用者） | Worker 自行擴大範圍（[C]）在 yolo 下沒有人確認 |
| 2. 熔斷計數器 | `worker_strikeout_action: warn` 的 `[A/B/C]` | 照 `block` 處理：三振出局格式回報、`PARTIAL` 或 `BLOCKED`、標準收尾 | 是否再試由塔台的 `yolo_max_retries`（斷點 B-1 / B-2）與 Renew 決定，不在 Worker 內另開一輪 |
| 3. 洋蔥偵測 | `[A/B]` 選項 | 新一層問題不在驗收條件內 → 照 [A]：記入回報區（表外發現），不追；它擋住驗收條件時，向塔台提問 | 追不追新問題是範圍決定 |
| 4. 超時提醒 | 「要繼續嗎？」、`[A/B]` | 不提問，只記入「互動紀錄」，在工單範圍內繼續 | 超時本身不是需要決定的問題；工單範圍不變，塔台從回報看得到耗時 |

這些事件照樣寫進「互動紀錄」，寫法比照 § 行為追蹤與互動紀錄，選項處改寫實際處理，例：
`[14:20] 🎓 範圍守衛（yolo）：要求修改 API format → 記入表外發現，未擴大範圍`。

## 四項防護機制

### 1. 範圍守衛（Scope Guard）

**偵測**：使用者要求做的事超出工單定義的任務範圍。

**觸發條件**（任一即觸發）：
1. 使用者要求修改工單未提及的子專案或模組
2. 需要跨工單的架構決策（影響多個 Story/Epic）
3. 需要讀取大量未在前置條件列出的檔案
4. 使用者追加的需求與原工單目標明顯不同

**判斷方式**：比對使用者的請求 vs 工單中的「任務指令」和「驗收條件」。

**範例**：

```
使用者：「順便把那個 API 的 response format 也改一下」

AI（sub-session）：
⚠️ 這個需求超出本工單（T0003）的範圍。

T0003 的任務是：修正 config.yaml 的 port 設定
T0003 的驗收條件是：port 改為 3000 且服務正常啟動

建議：
  [A] 先完成當前工單，回塔台開新工單處理
  [B] 記錄到工單「遭遇問題」，由塔台決策
  [C] 你確認要在本 session 擴展處理（風險：上下文不足可能導致錯誤）
```

**使用者選 C 時**：Worker 執行但在回報區「互動紀錄」明確標註「⚠️ 範圍擴展：<擴展內容摘要>」。

**升級行為**：

| 次數 | 行為 |
|------|------|
| 第 1 次離題 | 完整教學 + ABC 選項（如上） |
| 第 2 次離題 | 簡短提醒：「⚠️ 這超出 T0003 範圍，先完成工單再回塔台提需求？[A/B/C]」 |
| 第 3 次離題 | 警告＋建議收尾：「⚠️ 你已經三次想做工單以外的事了。建議我們先把 T0003 收尾，回塔台一次處理所有新需求。」 |

### 2. 熔斷計數器 / 三振出局（Fuse Counter / Strikeout）

**偵測**：同一個問題連續嘗試多輪未解決。

**「一輪」定義**：一次有意義的修改 + 驗證結果。

**計數方式**：追蹤「針對同一個錯誤/問題的嘗試次數」。當同一個 error 或同一段程式碼被修改達到 `worker_max_retries`（預設 3）次仍未通過驗證，觸發熔斷。

**Config**：
- `worker_max_retries`：最大嘗試輪數（1-10，預設 3）
- `worker_strikeout_action`：`block` = 禁止繼續（預設）/ `warn` = 警告但允許

**達到 max_retries 時（`worker_strikeout_action` = `block`）**：

Worker 禁止進入下一輪嘗試，以結構化格式回報並觸發收尾：

```
🚨 三振出局 — 問題未解決，回報塔台

問題描述：<一句話>
嘗試 1：<方法> → <結果>
嘗試 2：<方法> → <結果>
嘗試 3：<方法> → <結果>

現況：<目前程式碼狀態，是否有殘留修改>
建議：<給塔台的建議方向>
```

工單狀態 → PARTIAL 或 BLOCKED，執行標準收尾流程後提示使用者回塔台。

**達到 max_retries 時（`worker_strikeout_action` = `warn`）**：

```
⛔ 熔斷提醒：這個問題我們已經試了 N 輪不同的方法，都沒有解決。

繼續在同一個 session 裡嘗試的效果會越來越差，因為：
1. 前面失敗的嘗試佔據了我的記憶空間
2. 我可能開始重複之前試過的方案
3. 越改越偏離原本的方向

建議的做法：
  [A] 我整理一份回報（試了什麼、各自為何失敗），你帶回 Tower 決策
  [B] 再試一輪，但這是最後一次，之後不管結果都收尾回報
  [C] 我覺得快解決了，讓我繼續（⚠️ 不建議，但尊重你的判斷）
```

**使用者選 [C] 後下一輪仍失敗**：

```
⛔ 又一輪也沒有解決。

我現在要強制收尾了。不是因為不想幫你，
而是繼續下去只會浪費 token 且品質越來越差。

正在整理回報摘要……（以三振出局格式輸出）
```

**後續輪次**：不再提供 [C] 選項，只有 [A] 收尾回報和 [B] 最後一輪。

### 3. 洋蔥偵測（Onion Detector）

**偵測**：修好一個問題後又冒出新的、不同層級的問題，使用者想繼續追。

**判斷方式**：工單的驗收條件已經部分滿足，但使用者要求處理一個**不在驗收條件中**的新問題。

**第 2 層問題出現**：

```
使用者：「config 改好了，但啟動後發現 CICD pipeline 壞了，幫我看一下」

AI（sub-session）：
🎓 config 修好了（驗收條件 1 ✅），但 CICD pipeline 是一個新問題，
不在 T0003 的驗收條件裡。

這是典型的「洋蔥式問題」——剝了一層，下面還有一層。
繼續在同一個 session 追的風險是：我的記憶會越來越雜。

建議：
  [A] 我先把 T0003 標記為「部分完成」，CICD 問題交回 Tower 開新工單
      （⭐ 推薦：乾淨的 session 處理乾淨的問題）
  [B] 這兩個問題高度相關，我解釋一下為什麼應該一起處理
```

**使用者選 [B] 且理由合理**（例如：直接因果關係）：

```
🎓 了解，這確實是直接因果關係。我繼續處理。
但如果 CICD 問題又引出更多問題，我們就收尾回 Tower。
```

**第 3 層問題出現**：

```
⛔ 這已經是第三層了（config → CICD → Docker image build）。

不管這些問題有沒有因果關係，繼續追下去我的記憶品質會嚴重下降。
我現在收尾，把目前的進展和發現寫到回報區。

收尾中……
```

### 4. 超時提醒（Duration Alert）

**偵測**：工單執行時間過長。

**觸發閾值表**：

| 工單預估時間 | 提醒時間 | 強制提醒時間 |
|------------|---------|------------|
| ≤15 分鐘 | 20 分鐘 | 30 分鐘 |
| 16-45 分鐘 | 預估 ×1.5 | 預估 ×2 |
| ≥46 分鐘 | 60 分鐘 | 90 分鐘 |
| 未預估 | 30 分鐘 | 60 分鐘 |

**提醒（第一次）**：

```
⏰ 工單 T0003 已經執行了 35 分鐘（預估 15 分鐘）。

目前進展：
  ✅ 已完成：config 修改
  🔄 進行中：CICD 問題排查

要繼續嗎？還是先收尾回 Tower？
```

**強制提醒（第二次）**：

```
⏰ 工單 T0003 已經執行了 50 分鐘（預估 15 分鐘的 3 倍以上）。

強烈建議現在收尾。超時通常意味著：
1. 工單範圍定義不夠精確（Tower 的問題，不是你的）
2. 遇到了預期外的問題（應該回 Tower 重新評估）
3. 追了洋蔥問題太深層（應該拆工單）

  [A] 收尾回報，讓 Tower 重新規劃
  [B] 再給我 10 分鐘，之後一定收尾
```

## 行為追蹤與互動紀錄

所有防護事件都要記錄到工單回報區的「互動紀錄」中：

```
## 互動紀錄
[14:20] 🎓 範圍守衛：使用者要求修改 API format → 引導回工單範圍 → 使用者接受
[14:35] ⛔ 熔斷計數器：第 3 輪失敗 → 使用者選 [A] 收尾回報
[14:38] ⏰ 超時提醒：35min/預估15min → 使用者選收尾
```

Tower 收到回報後可以從互動紀錄中了解 sub-session 發生了什麼，用於：
1. **判斷工單設計問題**：頻繁觸發範圍守衛 → 工單範圍定義不夠明確
2. **判斷估時問題**：頻繁超時 → 估時需要校準
3. **判斷使用者習慣**：頻繁死纏爛打 → beginner 教學進度需要調整
4. **回饋 insights**：`/ct-insights` 可以分析這些事件的頻率和趨勢

## Beginner / Standard / Expert 三級差異表

| 防護機制 | Beginner 模式 | Standard 模式 | Expert 模式 |
|---------|--------------|--------------|------------|
| 範圍守衛 | 完整教學 + ABC 選項 | 簡短提醒 + ABC | 關閉 |
| 熔斷計數器 | `max_retries` 輪觸發 + 三振出局格式 + 強制收尾 | `max_retries` 輪提醒 + 依 `strikeout_action` 決定 | 關閉（靜默記錄） |
| 洋蔥偵測 | 第 2 層就提醒 + 第 3 層強制收尾 | 第 3 層提醒 + 不強制 | 關閉 |
| 超時提醒 | 兩階段（提醒 + 強制提醒） | 單次提醒（不強制） | 關閉 |
| 行為追蹤 | 每個事件都記錄到互動紀錄 | 只記錄熔斷和強制收尾事件 | 熔斷計數器靜默記錄（不提醒，但寫入互動紀錄供 insights 分析） |

## experience-level 來源判定

防護等級由以下優先級決定：

1. 工單元資料中的 `experience-level` 欄位（若存在，以工單為準）
2. `_tower-config.yaml` 中的 `experience-level` 設定
3. 預設值：`standard`
