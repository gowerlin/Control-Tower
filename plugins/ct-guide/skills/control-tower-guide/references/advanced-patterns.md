# 進階使用模式

本檔收錄單張工單流程以外的情境：跨專案與多塔台、中斷、mono-repo、除錯與品質閘門、Worker 執行期防護、
新手村、學習與 FIELDGUIDE、歸檔與遷移、塔台自主 commit。
派工機制見 `runtime-dispatch.md`；落點檢查、單一權威定義等治理護欄的設計理由見 `governance.md`。

## 跨專案協調

當一個需求影響多個專案（各自有自己的 `_ct-workorders/`），CT 提供正式的協調機制。
同一個專案裡開多個塔台 session 是另一回事，見下方〈多塔台〉。

### 五種協調類型

前三種是**工單**，後兩種是**非工單的跨塔台通道**：

| 類型 | 工單？ | 說明 | 使用情境 |
|------|-------|------|---------|
| **LOCAL** | ✅ | 預設，單專案工單 | 一般任務，省略協調區段 |
| **COORDINATED** | ✅ | 統籌工單，追蹤跨專案整體進度 | 需求影響多個專案，由主專案建立 |
| **DELEGATE** | ✅ | 受派工單，參照統籌工單或 HANDOVER 執行 | 接收專案依子任務描述建立 |
| **HANDOVER** | ❌ | 受理**前**的發現＋提案，尚未成為工單 | 發現了對方負責的問題，但修法要由對方判斷 |
| **ADVISORY** | ❌ | 純意見，**不期待對方動作** | 對他方的可選強化提供評估，明確不主張必改 |

HANDOVER／ADVISORY 不進工單編號序列、不計入熱區統計、不受 `*sync` 狀態掃描管轄。

### 為什麼三種不夠

原本只有 LOCAL／COORDINATED／DELEGATE。一次真實的跨塔台交辦暴露了三個缺口：

| 缺口 | 問題 | 補上的形狀 |
|------|------|-----------|
| 沒有「受理前提案」 | COORDINATED 假設統籌方已知各專案該做什麼；但常見情況是「我查到這些、我猜你們該這樣改、你們自己判斷」——發起方**無權也無資訊**替對方定義子任務 | **HANDOVER** |
| 沒有「純諮詢」通道 | 為一個意見開 DELEGATE，等於把「意見」說成「派工」，逼對方在沒有承諾的事情上背狀態 | **ADVISORY** |
| 沒有「反駁前提」的位置 | DELEGATE 的回報區是**完工回報**用，不是**動工前更正來源前提**用 | 回覆稿的**異議段落** |

### HANDOVER 與 ADVISORY 怎麼運作

- **發起方**把 `_handover-<日期>-<主題>.md` 寫在**自己的** `_ct-workorders/`；**接收方**把 `_reply-<日期>-<主題>.md` 寫在**自己的** `_ct-workorders/`，由使用者轉交
- 檔名的 `_` 前綴讓它們自然落在 `T####` 掃描之外，不需要額外排除規則
- HANDOVER 的終點是 `ACKNOWLEDGED`（受理，接收方建立 DELEGATE 工單並記下編號）或 `DECLINED`（不受理，回覆稿須載明理由），不是 `DONE`
- ADVISORY 用同一套格式，但**不得**填受理後的工單編號——填了就表示它其實是 HANDOVER

### 跨 session 通知對方塔台（v5.9.0）

「由使用者轉交」很穩，但慢。兩座塔台都是 Claude Code 時，塔台可以用 Claude Code 的跨 session 訊息（ListAgents 列出 session、SendMessage 送訊息）
直接通知對方——問題是**送給誰**。Claude Code 沒命名的 session 在 ListAgents 上只叫「目錄名＋兩字元」（例 `better-agent-terminal-93`），
看不出哪個是塔台、哪個是 Worker。2026-10-18 就真的把完工回覆送給了 BAT 的 Worker。

CT 沒有向 Claude Code 提需求，而是請 BAT 解決（D067）：BAT `>= 0.7.1-pre.1` 啟動 claude 分頁時用 `--name` 命名——
Worker 叫 `<工作區> · Worker · T####`，用 BAT「以塔台開啟 Claude」開的分頁叫 `<工作區> · Tower`，其他分頁叫 `<工作區> · <短 ID>`。
CT 這邊的規則是三步，命中就停：

1. ListAgents 有 `<目標工作區> · Tower` → 送它
2. 自己在 BAT 內、且已宣告塔台 → 用 MCP `bat_list_terminals scope=towers` 問 BAT「這台機器上有哪些塔台」，以工作區名稱找到對方，
   拿它的 `claudeSessionName` 到 ListAgents 對名稱
3. 都找不到（對方是 codex 塔台、在別台機器、舊 BAT、非 BAT）→ 回到老做法：回覆稿寫在自己 repo，請使用者轉交

兩條不能鬆的線：名稱裡有 ` · Worker · ` 的 session **一律不是塔台**；**不准猜**——不能靠目錄名或 idle／busy 狀態推定誰是塔台，
推不出來就走第 3 步。另外，跨 session 訊息只是**通知**，`_handover-*.md`／`_reply-*.md` 仍是正式紀錄，檔案照舊寫在自己 repo；
訊息第一行也仍請對方先確認自己是塔台——`· Tower` 只代表分頁怎麼開的，BAT 不會替它宣告塔台。

> 選收件人的順序、名稱格式與例外以 CT 的 `cross-project-coordination.md` § 跨 session 選收件人 為準；
> `scope: towers` 與兩個新欄位的設計理由見 `bat-integration.md` § 查詢通道。本節只講為什麼。

### 回覆稿的異議段落

接收方的回覆稿**允許並鼓勵**「更正來源塔台前提」。理由只有一句：**接受錯誤的根因描述，會導致錯誤的修法。**

實例：來源塔台診斷為「CT skill 沒有 `--workspace` 旗標」；查證後該旗標早已存在，真正的缺陷是 SKILL.md 的派工指令行是有損摘要。
照原診斷去修，只會補一個旗標，下一個被省略的旗標會原樣重演（這正是 `governance.md` § 摘要授權規則的由來）。

異議段落要寫：來源前提原文、查證結果與證據（檔案:行號）、修正後的根因、對修法的影響。
**異議不是拒絕受理**——受理與更正前提可以同時成立。

### 協調流程

```
Step 1  統籌塔台建立 COORDINATED 工單（含各專案子任務描述）
Step 2  使用者到接收專案的塔台，告知來源工單
Step 3  接收塔台【唯讀讀取】來源工單，建立 DELEGATE 工單
Step 4  Worker session 執行 DELEGATE 工單（標準 ct-exec 流程）
Step 5  使用者回統籌塔台回報，統籌塔台讀取對方工單確認
Step 6  所有子任務的 DELEGATE 皆 DONE → 統籌工單 DONE
```

**唯讀原則**：接收塔台只讀不寫來源專案的檔案；所有修改只發生在自己專案的 `_ct-workorders/`。
跨專案工單的關聯記在各自的 `_cross-references.md`，塔台建立新工單前會先查它，發現相關主題就提醒使用者。

### 統籌權

統籌權**不固定**：誰先碰到需求，誰自然成為統籌者；受影響最大的專案可主動接手；共用程式庫（如 `shared/`）不設工單目錄，由受影響最大的服務代理統籌。
若發現另一專案更適合統籌，原統籌工單標記轉移、改為 DELEGATE，新統籌專案另建 COORDINATED 工單引用原工單。

### 工單 ID 前綴

跨專案協調時，前綴讓工單編號全域可辨識（例如 `LC-T0001`）。前綴的**來源有二**：

1. **`project-prefix` 設定**——一旦設定，塔台派發**所有**工單都無條件加上前綴，不分是否跨專案
2. **跨塔台交辦的既有慣例**（如 `CP-`）——由他方塔台或人工建立的協調工單，不經 `project-prefix` 產生

所以**沒設 `project-prefix` 的專案，一樣可能出現前綴 ID**。任何「本專案沒設前綴，所以只會看到 `T####`」的假設都是錯的，
處理工單 ID 的任何地方（`*sync`、`*archive`、派工參數、YOLO 回報比對）都必須接受帶前綴的 ID。
反過來也一樣：Worker **送出**的 ID（通知、提問、`--source`）必須是含前綴的完整 ID，否則 BAT 對不上 Worker 分頁（v5.13.1，見 `work-order-lifecycle.md` § 回報與通知用完整工單 ID）。
ID 的合法格式只有一處權威定義（`work-order-system.md` § 工單 ID 格式）；為何要收斂成一處，見 `governance.md` § 單一權威定義。

## 多塔台

### 同一專案的多個塔台 session

例如 Feature 與 Hotfix 平行作業。工單檔案、`sprint-status.yaml` 天然共享；各塔台在 `_ct-workorders/_tower-registry.md` 登記範圍、分支與鎖定的工單，
並透過跨塔台留言板交換訊息；各自的對話與推理則由 context window 天然隔離。

### 跨塔台 GP 命名空間（D62）

同一台機器上跑多個 repo 的塔台時，它們共用同一個 Layer 2 目錄 `~/.claude/control-tower-data/`。
`*evolve --playbook` 晉升的全域 playbook 原本用「全域最大 GP 編號 + 1」編號，結果兩個塔台各自算出相同編號——實際撞號後只能手工改號補救。

D62 改用**命名空間前綴**：

```
舊：GP###（全域共享，會撞）
新：GP-<PREFIX>-###（每個塔台一個 namespace）
```

每個塔台在自己的 `_tower-config.yaml` 設定 `gp-prefix`（2–4 字大寫），晉升時只在自己的 namespace 裡取最大值 + 1。
**寫入前不需鎖、不需同步、不需中央登記簿**；兩個塔台同時晉升也不會重號。前綴採「先到先得，事後告知」，取用前先看一次現有前綴清單。

D62 **不溯及既往**：舊的無前綴編號凍結、不改名、舊引用照樣有效；新晉升則**不得**再產生無前綴編號。
未設定 `gp-prefix` 時，晉升會暫時退用 `project-prefix`；兩者都沒設就警告並拒絕晉升，但不影響其他塔台。
這個 fallback 只是緊急防呆：`project-prefix` 的語意是工單前綴，與 GP 命名空間不同，CT 建議明確設定 `gp-prefix`。

這與上一節的思路相同：與其在共享資源上加鎖協調，不如把命名空間切開，讓每個參與者自治。

## 中斷處理（`*pause`／`*resume`）

開發中被插件是常態。遇到緊急任務時，在塔台輸入 `*pause` 加一句說明，而不是自己跳出去處理：

```
*pause 上線版本 v2.1 的登入 API 回 500，客戶在催
```

塔台會：

1. **凍結**當前工單為 `PAUSED`，把暫停原因與時間記入工單檔
2. 在 `_tower-state.md` 記錄暫停狀態
3. 以選項式提問評估緊急任務的範圍、影響、是否需要不同分支
4. 派發 🔥 `URGENT` 工單（不經 `PENDING`），附分支策略建議
5. 排入回歸佇列，確保原任務接得回來

`*resume`（或 `*resume T0005` 指定工單）時，塔台把緊急工單標記完成、顯示暫停時的上下文摘要、把原工單改回 `IN_PROGRESS`、
清除暫停紀錄，並提醒兩件容易漏的事：**緊急修改是否影響暫停中任務的設計**，以及 **feature 分支是否需要 merge main**。

緊急任務在不同分支時，建議用 `git worktree` 物理隔離，兩個目錄各自開 session。小 hotfix 由同一塔台管理、工單指定 worktree 路徑；
複雜或時間不定的 hotfix 開第二個塔台，完成後關閉。

## Mono-Repo 管理

一個塔台管理多個子專案時，啟動時先告訴塔台結構（各子專案的用途、是否有獨立 `.git`、共用模組在哪）。塔台額外負責：

- **工單標記目標子專案**——body 元資料的「目標子專案」，對應 frontmatter 的 `project` 欄位（與落點檢查用的 `repo` 是不同欄位，見 `work-order-lifecycle.md` § frontmatter 欄位地圖）
- **跨子專案影響偵測**：改到共用模組時提醒兩邊都要測試
- **文件歸屬建議**：共用文件放上層 `docs/`，子專案特有的放各自目錄；每個 Story 完成後提醒檢查文件與程式碼是否一致

同一需求要在多個子專案實作時：

```
邏輯完全相同          → 抽到共用模組
規則相同、技術棧不同  → 先做一、後參照：先派 A 的工單（spec + 實作 + 測試），
                         完成後派 B，附參照實作路徑、一致性要求、可變範圍、必須覆蓋的測試案例
規則不同              → 各自獨立派發，互不相依
```

## 三層除錯防線

Worker 遇到問題時，塔台依序建議三層防線：

| 層 | 作法 | 適用 |
|----|------|------|
| **第一層：TDD／ATDD（預防）** | 先寫測試定義預期行為，開發目標變成「紅 → 綠」 | 功能邏輯錯誤、邊界條件遺漏、併行資料干擾 |
| **第二層：診斷腳本（自動化偵測）** | 派「診斷工單」讓 Worker 寫診斷腳本，使用者執行後把結果寫入回報區；目標是把 10000 行 log 濃縮成 20 行結論 | 難以重現、log 量大、需要統計分析 |
| **第三層：結構化 log 分析（最後手段）** | 提供 grep／jq／awk 預處理指令讓使用者先過濾，過濾後上限 50 行 | 前兩層都不適用時 |

貫穿三層的鐵律：**原始 log 絕不直接貼進任何 AI session**——不只是塔台，Worker 也一樣。
原始 log 是低密度資料，貼進去只會燒掉 context；先用工具濃縮，AI 才能用在判斷上。

## 品質閘門

審查類工單的回報包含 **CRITICAL 或 HIGH** 發現時：

1. **強制**派發修正工單，不得直接進入下一階段
2. 修正完成後可選擇派發覆核工單（原始 CRITICAL 超過 5 項時建議）
3. 進度表標記：審查 ✅ → 修正 🔄 → 下一階段

**交叉驗證原則**：產出文件的 session 與審查它的 session 必須分開，避免確認偏誤；審查類工單建議開新 session。
這條規則來自實戰：曾經跳過修正步驟直接往下走，被使用者糾正。

## Worker 執行期的四項防護

`ct-exec` 執行期間持續監控四件事，防止 Worker session 離題、死纏爛打、無限延伸。
四項防護都**不替使用者做決定**，而是在關鍵時刻把選擇攤開，並記入回報區的互動紀錄。

> **yolo 下（v5.5.1）**：yolo Worker 不問使用者（`work-order-lifecycle.md` § yolo 提問通道），所以下面各項「把選擇攤開給使用者」的那一步改掉——
> 範圍守衛一律照 [B] 記錄、不擴大範圍；熔斷的 `warn` 照 `block` 收尾（要不要再試，由塔台的斷點 B 與 Renew 決定）；洋蔥問題記入表外發現；超時只記錄。
> 不先決定就無法完成工單時，Worker 改問塔台。非 yolo 照下文。確切規則見 CT `ct-exec/references/session-guardrails.md` § yolo 下的處理。

### 1. 範圍守衛（Scope Guard）

使用者要求的事超出工單範圍時觸發——例如要動工單沒提到的子專案或模組、需要跨工單的架構決策、
需要大量讀取前置條件沒列的檔案、或追加的需求與原目標明顯不同。Worker 提示：

```
⚠️ 這個需求超出本工單（T0003）的範圍。

  [A] 先完成當前工單，回塔台開新工單處理
  [B] 記錄到工單「遭遇問題」，由塔台決策
  [C] 你確認要在本 session 擴展處理（風險：上下文不足可能導致錯誤）
```

使用者選 [C] 時 Worker 照做，但在互動紀錄明確標註「⚠️ 範圍擴展」與擴展內容。
同一 session 第二次離題只簡短提醒，第三次則建議先收尾、回塔台一次處理所有新需求。

### 2. 熔斷計數器／三振出局

同一個問題連續嘗試多輪仍未解決時觸發。「一輪」是一次有意義的修改＋驗證結果；同一個錯誤或同一段程式碼被修改達 `worker_max_retries`（預設 `3`）次仍未通過，就熔斷。
之後的行為由 `worker_strikeout_action` 決定：

| 值 | 行為 |
|----|------|
| `block`（預設） | 禁止進入下一輪，以結構化格式回報（問題、每次嘗試的方法與結果、現況、建議），工單轉 `PARTIAL` 或 `BLOCKED` 並收尾 |
| `warn` | 提醒並給選項：整理回報帶回塔台／再試最後一輪／繼續；選「繼續」後下一輪仍失敗即強制收尾，之後不再提供「繼續」 |

**為什麼要三振？** 失敗的嘗試會佔據 context，AI 會開始重複試過的方案、越改越偏。
停下來把「試過什麼、為何失敗」交回塔台，讓塔台用全局視角重新評估，比在同一個 session 裡硬撐有效。

### 3. 洋蔥偵測（Onion Detector）

修好一個問題後又冒出一個**不在驗收條件裡**的新問題、使用者想繼續追時觸發——剝了一層，下面還有一層。

- 第 2 層出現：建議 [A] 本工單標記部分完成，新問題交回塔台開新工單（推薦：乾淨的 session 處理乾淨的問題）；
  或 [B] 由使用者說明兩者為何高度相關（例如直接因果）——理由合理就繼續
- 第 3 層出現：不論是否有因果關係都收尾，把進展與發現寫進回報區

它與範圍守衛的差別：範圍守衛處理「使用者提出別的事」，洋蔥偵測處理「工作本身一路往下長」。

### 4. 超時提醒（Duration Alert）

工單執行時間遠超預估時觸發：

| 工單預估 | 提醒 | 強制提醒 |
|---------|------|---------|
| ≤ 15 分鐘 | 20 分鐘 | 30 分鐘 |
| 16–45 分鐘 | 預估 ×1.5 | 預估 ×2 |
| ≥ 46 分鐘 | 60 分鐘 | 90 分鐘 |
| 未預估 | 30 分鐘 | 60 分鐘 |

強制提醒時會點出超時通常代表的三件事：工單範圍定義不夠精確（塔台的問題，不是使用者的）、遇到預期外的問題、或洋蔥追得太深——都該回塔台重新規劃。

### 防護強度與 `experience-level`

| 防護 | beginner | standard | expert |
|------|---------|---------|--------|
| 範圍守衛 | 完整說明＋ABC | 簡短提醒＋ABC | 關閉 |
| 熔斷計數器 | 觸發即三振格式＋強制收尾 | 提醒，依 `worker_strikeout_action` | 關閉（靜默記錄） |
| 洋蔥偵測 | 第 2 層提醒、第 3 層強制收尾 | 第 3 層提醒、不強制 | 關閉 |
| 超時提醒 | 兩階段 | 單次、不強制 | 關閉 |

等級依序取自工單的 `experience-level` 欄位、專案設定、預設 `standard`——這類防護強度屬於調諧參數，不是 Worker 的 runtime 模式（見 `concepts.md` § Worker 無狀態）。

### 互動紀錄的用途

所有防護事件都寫進回報區的互動紀錄，塔台據此判讀的是**工單設計**而不只是這一次執行：
頻繁觸發範圍守衛 → 工單範圍定義不清；頻繁超時 → 估時需要校準；頻繁熔斷 → 新手教學進度需要調整。
`ct-insights` 也會分析這些事件的頻率與趨勢。

## 新手村教學模式

`experience-level` 為 `beginner` 時，塔台載入教學模式（它是塔台內建的 reference，不是獨立 skill）。
首次啟動時若既沒有 `_tower-state.md` 也沒有 `_learnings.md`，塔台也會判定為新手。

### 六個教學關卡

| 關卡 | 主題 | 觸發時機 |
|------|------|---------|
| 0 | 啟動與認識塔台 | 首次啟動；說明塔台與 Worker 的分工 |
| 1 | 第一張工單 | 準備派發第一張工單時 |
| 2 | 違規偵測與即時糾正 | 在塔台貼程式碼、要塔台直接改檔、問技術細節時 |
| 3 | 第一次回報 | 第一次從 Worker 回來回報時；養成帶工單編號的習慣 |
| 4 | 第一次遇到問題 | 在 Worker 遇到問題回來問、或貼了大量 log 時 |
| 5 | 畢業 | 完成 3–5 張工單、且最近 3 張沒有觸發任何糾正 |

畢業**不是自動升級**，而是提議：[A] 升級到 `standard`；[B] 再練幾張；[C] 升級但保留違規提醒（以簡短提醒模式運作）。
教學進度記在 `_tower-state.md` 的教學區段，跨 session 保存。

### 遞減提醒與語氣

同類違規：第 1 次完整說明（約 10 行）→ 第 2 次一句提醒 → 第 3 次一個詞 → 第 4 次以後不再提醒，避免惹惱使用者。
語氣是「等一下！」而不是「你做錯了」；每次糾正都附正確做法，並尊重自主——問「要我幫你派工單嗎？」而不是直接派。

## ct-insights：使用模式分析

| 範圍 | 呼叫 | 資料 |
|------|------|------|
| 專案 | `/ct-insights`（或 `$ct-insights`） | 本專案的工單、塔台狀態、決策、learnings、sprint 狀態 |
| 全域 | `/ct-insights global` | Layer 2 專案索引與各註冊專案摘要 |

分析狀態分布、週期時間、BLOCKED／PARTIAL 比例、重試與三振訊號、停滯的進行中項目，辨識好壞模式與原則衝突，
並依影響與成本排序建議。

報告規則反映它的定位——**健檢儀不能自己造假**：先列發現並附工單編號或檔案證據、區分觀察事實與推論、不從不完整的紀錄過度推論；
工單少於 3 張時明說樣本太小，只給局部觀察。

**Workflow 適配度（v5.10.0+）**：`ct-insights` 也能回答「哪些工作適合用 Claude Code Workflow 執行」。規則組分兩條軌道——
**扇出軌**看單張工單是否明文列出 3 個以上、執行前就能列出、彼此獨立的同形子項（S1＋S6）；**驗證軌**看這類工作是否常被推翻或改判（S3）。
排除條件 X1–X5 擋掉需要人工實機驗證、執行中要人回答、跨 session、機械批次的工作，以及「重複在工單之間」的序列（轉 Playbook）。
結果只分 🔵 候選／邊界／排除，**不打 0–100 分數**：試點時腳本分數平均高估約 21 分，決定成敗的其實是兩個是非條件（子項是否獨立、是否被推翻過）。
輸出是 `WFC###` 候選，`ct-insights` 本身不寫 brief、不執行 Workflow。權威：CT `ct-insights/references/analysis-rules.md` § Workflow 適配度。

**預篩腳本：守門與按需提示（v5.11.0+）**：同一套規則也寫成腳本 `ct-insights/scripts/ct-workflow-prefilter.py`，隨 skill 發行（Python 3 標準函式庫、不呼叫 LLM、0 token）。它只有兩個角色：① **排除守門**——命中 X2（執行中要人即時回答）、X3（跨 session）、X5（序列重複，改提示 Playbook）的工單，塔台不必考慮 Workflow；② **按需提示**——塔台主動打 `*insights workflow` 或 `*insights workflow T0123` 時，列出候選與證據行號。它**不自動標記、不修改工單**，也不在派工流程裡自己跑。為什麼只拿 X2／X3／X5 守門？因為跨專案校準時，腳本對 X2 的召回與誤判和 T0177 定案結果相同，而 X1、X4 這類要看語意的條件召回只有 15–25%；「該用 Workflow」的正向判斷更不準（抽讀 9 張候選只有 2 張成立）。準的拿來擋、不準的只在被問時才說——這是 CT 一貫的「會誤報的守門員沒人理」。v5.11.0 也修了三種誤判：決策型工單（`decision-requiring`、DP 裁定紀錄）沒被 X2 擋下、逐項語氣只寫在標題、「逐一複製／雜湊／計數」這類機械批次。權威：同檔 § 預篩腳本：排除守門與按需提示。

## ct-evolve：學習萃取

`ct-evolve` 回答「我學到了什麼」，把執行歷史蒸餾成可複用知識，而不是把原始事件堆進長期記憶。
Tactical／Strategic／Episodic 三類的定義與寫到哪一層，見 `three-layer-arch.md` § 學習紀錄的分流；四級成熟度管線見 `concepts.md` § 知識成熟度管線。

### Distillation Gate

每個候選在寫入前都要回答五個問題：發生了什麼？為什麼？在什麼觸發條件下會重演？代表什麼一般性模式？未來的 agent 該採取什麼具體動作？

**需要回顧原始事件才看得懂的候選，一律退回或歸入 Episodic。** 合格的 learning 要能在另一個任務裡當成 if-then 規則使用，
因此每筆以 Trigger／Pattern／Action／Example 四欄為核心，另記來源與成熟度。

這道閘門防的是「把事件當知識」：事件紀錄只對經歷過的人有意義，換一個任務就無法套用。

### FIELDGUIDE 橋接

蒸餾出的候選若與 coding 標準、UI 慣例、命名、API 格式、驗證、錯誤處理或設計 token 有關，`ct-evolve` 會加上 `[FG-CANDIDATE]` 標記與主題，
之後由 `ct-fieldguide` 晉升進 FIELDGUIDE 或 DESIGN.md。學習管線與 FIELDGUIDE 因此是同一條流水線的兩段。

### Workflow 橋接與 `--workflow`（v5.10.0+）

同樣的橋接也接到 Workflow：候選若符合 `ct-insights` Workflow 適配度的 🔵 候選等級，`ct-evolve` 加上 `[WF-CANDIDATE]` 標記。
`/ct-evolve --workflow [name]` 再把它寫成 **brief**——子任務來源、階段與每階段 schema、驗證策略、是否需要 worktree、規模上限與成本預估——
並存成 🔵 知識卡（`_ct-workorders/_workflows/<name>.md`）。

它**只產 brief**：不寫 `.claude/workflows/` 腳本、不執行 Workflow、不回測。這和 `--skill` 停在 brief 是同一個理由——
真正會花錢、會改專案的那一步，要先讓使用者看過設計再另開工單。定位與三分法見 `concepts.md` § Workflow：單張工單內的執行方式；
權威見 CT `ct-evolve/SKILL.md` 與 `control-tower/references/workflow-engine.md`。

v5.11.0 起在塔台 session 打 `*evolve --workflow [name]` 也可以：塔台直接轉交 `/ct-evolve --workflow`，不另做一套（權威 CT `playbook-engine.md` § `*evolve` 擴展子命令）。

## FIELDGUIDE 教戰手冊

FIELDGUIDE 是專案級的 coding 標準文件，內部分三層：

| 層 | 名稱 | 回答 |
|----|------|------|
| L1 | 設計哲學 | 為什麼——不隨技術改變的原則 |
| L2 | 決策樹 | 怎麼選——特定情境的 if-then 判斷 |
| L3 | 專案快照 | 具體怎麼做——本專案的路徑、元件名 |

> 注意：這是 FIELDGUIDE **文件內部**的分層，與 `three-layer-arch.md` 談的兩種「三層」都不同，不可混用。

### `ct-fieldguide` 與 `*fieldguide` 的分工

| | `ct-fieldguide`（Worker skill） | `*fieldguide`（塔台內建） |
|---|---|---|
| 做什麼 | 實際掃描、寫入 | 只讀取與分析，產出是工單 |
| 子命令 | `init`、`update`、`audit`、`audit --debt`（找同一慣例的多種競爭實作）、`extract`、`merge`、`promote`（評估晉升全域）、`design`（從程式碼或 URL 產出或稽核 DESIGN.md） | `scan [N]`、`add [topic]`、`audit [module]`、`init`、`debt [topic]`、`design`（含 `generate`／`check`） |

`*fieldguide` 的每個寫入動作都透過工單交給 `ct-fieldguide`——這是塔台不碰檔案內容的同一條邊界。
`ct-fieldguide` 不確定意圖時偏好唯讀的 `audit`，而不是寫入。

DESIGN.md 是視覺規範（token、字級與間距、色彩、元件狀態、斷點、無障礙）的單一來源，FIELDGUIDE 不重複寫視覺規則，只連結或橋接。

### Global／Project 分層與晉升

```
Global（~/.claude/control-tower-data/fieldguide/）
├── seed-l1.md            ← 跨專案通用的 L1
├── seed-l2-templates.md  ← 可複用的 L2 骨架
├── promoted/             ← 從專案晉升的完整 L1＋L2（不含 L3）
└── registry.md           ← 跨專案 FIELDGUIDE 索引

Project
└── FIELDGUIDE.md         ← 自包含，init 時從 Global 種子注入
```

L1／L2 在 2 個以上專案出現相同內容時可晉升到 Global；**L3 永不晉升**，它本質上就是專案特定的。

### 標記系統

| 標記 | 含義 | 誰寫 |
|------|------|------|
| `[FG]` | coding 標準發現 | 工單回報區 |
| `[FG-DEBT]` | 技術債：同一議題多種做法 | 工單回報區 |
| `[FG-PROMOTE]` | 建議晉升 Global | 工單回報區 |
| `[FG-CANDIDATE]` | 蒸餾出的候選 | `ct-evolve` 寫在 `_learnings.md` |
| `[WF-CANDIDATE]` | 適合 Workflow 的工作形狀（v5.10.0+，不屬於 FIELDGUIDE；由 `ct-evolve --workflow` 接手） | `ct-evolve` |

`*fieldguide scan` 有兩種擷取模式：有標記的內容直接擷取（精確）；沒有標記時，從「遭遇問題」與「互動紀錄」裡的技術決策描述推斷（補充），並標注「語義推斷」提醒使用者確認。標記越齊全，萃取越不需要猜。

## 歸檔操作

歸檔資格（終態依類型、`archive_days`、引用式豁免）的設計見 `concepts.md` § 熱區／冷區分離；冷區位置見 `three-layer-arch.md`。這裡只補操作面：

| 語法 | 行為 |
|------|------|
| `*archive` | 掃描熱區 → 列出候選 → 確認 → 批次 `git mv` |
| `*archive --dry-run` | 只列出候選，不執行 |
| `*archive T0001` | 強制歸檔指定單據，跳過天數與引用檢查（會顯示警告） |
| `*archive --search <關鍵字>` | 在冷區搜尋已歸檔單據 |
| `*archive --restore T0001` | 從冷區取回熱區 |

豁免不靠在單據上加旗標，而是**看引用關係**：仍被進行中單據引用、被塔台釘選或在待處理事項中提及、跨專案協調中對方尚未完成——都自動豁免。
旗標會過時（引用解除了，旗標還在）；引用關係每次都重新計算，所以不會。

研究、規格等參考文件（`_spec-*.md` 等）完全不在歸檔範圍內，見 `integration.md` § 研究／Spec 文件。

從 v3.6 專案升級時，塔台在啟動主面板之後偵測 8 項 v4 功能是否已啟用：

| # | 偵測項 | 遷移動作 |
|---|--------|---------|
| 1 | `_ct-workorders/_archive/` 冷區 | 建立三個子目錄 |

## 塔台自主 Commit

塔台硬邊界的「唯一直接處理例外」（見 `concepts.md` § Hard Boundaries）——單一模組內、不涉邏輯的小變動——完成後的 commit 行為由 `auto_commit` 決定：

| 值 | 行為 |
|----|------|
| `on` | 靜默自主 commit |
| `ask`（預設） | 修改完成後詢問使用者 |
| `off` | 不 commit，只回報修改內容 |

適用條件是三件事同時成立：**粒度小、無邏輯變動、單一模組**。硬限制——涉及邏輯、跨模組、使用者禁止——不受 `auto_commit` 影響，一律派工單。
commit 訊息依 `auto_commit_format` 模板產生（預設 `chore: {description} ({scope})`）；塔台 commit 時只納入目標檔案，保留無關的未提交變更。

`auto_commit` 只管塔台自己的小修改；Worker 收尾的 commit 由 `worker_commit` 與工單決定（見 `work-order-lifecycle.md` § Phase 4）。
