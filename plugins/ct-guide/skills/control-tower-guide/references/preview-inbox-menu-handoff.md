## 一句話

**選單開著時在待辦分頁回答也算數：BAT 先關掉選單、再把你的回答送給塔台；被關掉的那幾題不會一直重開，你在待辦分頁或終端接著答就好。**

---

## 發生了什麼

塔台暫停時，先把待決項目寫進 `_tower-state.md`（`awaiting_user`），再開 Claude Code 的原生選單；BAT 的待辦分頁同時列出同一題。
兩邊都看得到題目，照理哪邊回答都可以。實際上選單開著時，終端在等的是選單的按鍵：在待辦分頁送出的回答被當成按鍵打進選單，
塔台收到的是選單的結果（BAT 實機遇到的是「兩題都放棄」），和你選的完全不同。

BAT 先自己修了一半：塔台分頁在等選單（`question` blocked）時，待辦分頁的回答改成 BAT 先代按 Esc 關掉選單、等選單真的關了，
再把回答以一行 `U-n：…` 送出。這一步不需要 CT 改，因為 CT 本來就說「Esc 之後，塔台照常接受文字回答」。

剩下的問題 BAT 自己解決不了：

- **BAT 只知道「有選單開著」，不知道選單裡是哪幾題。** 你回答的 `U-n` 不在這個選單裡時（例：選單問的是別的事），代按 Esc 會關掉一個不相干的選單。
- **一個選單常有好幾題。** Esc 會把整個選單關掉，其他題也一起取消。塔台之後要不要重開？如果每答一題就重開一次，BAT 又得 Esc 一次，就變成循環。

這兩件只有寫狀態檔的塔台說得清楚，所以由 CT 補。

---

## `menu_open`：為什麼由塔台寫出選單裡的題目

塔台開選單前，在寫 `awaiting_user` 的**同一次寫入**多寫一個頂層欄位：

```yaml
menu_open:
  ids: ["U-57", "U-58"]
  opened_at: "2026-11-28T12:23:00+08:00"
```

- `ids` 是這個選單裡的 `U-n`，照選單的題目順序；每一筆都必須同時在 `awaiting_user` 裡。選單一次最多 4 題，所以 1～4 筆。
- `opened_at` 是寫入時間，取自系統時間（和契約 v2 其他新欄位一樣用 `+08:00` 帶冒號的寫法）。

**為什麼放在「開選單前」那一次寫入。** 塔台一開選單，這一回合就停在選單上，等你作答或按 Esc——選單開著的時候塔台不會再寫檔。
所以「選單裡有哪些題」只能在開之前寫好；而 CT 本來就規定先寫待決、再開選單（暫停的提問方式第 1 點），順手寫在同一次寫入最省事。
（「同一次寫入」實際上可能被拆成幾個 Edit，中間會有一瞬間不合法——這是 pre.1 驗收時發現的，見下方〈pre.2：為什麼 `menu_open` 要緊接 `awaiting_user`〉。）

**BAT 拿它做什麼。** BAT 只在兩個條件同時成立時才代按 Esc：塔台分頁確實在等選單（`question` blocked），而且你回答的 `U-n` 在 `menu_open.ids` 裡。
不在裡面就照舊把回答保留到選單關閉——關掉一個不相干的選單比晚一點送到更糟。`opened_at` 讓 BAT 對得上「這個欄位是不是現在這個選單的」：
CT 一定是先寫檔、幾秒內就開選單，時間差太多的就當作殘留、不採信。細節以 BAT 文件為準。

**什麼時候不寫。** 只有選單裡至少有一筆 `U-n` 才寫。需求對齊等不含 `U-n` 的選單不寫——對 BAT 來說就是「開著的選單裡沒有待辦分頁的題」，照舊保留回答。
不開原生選單的情況當然也不寫：Codex 塔台、BAT 契約不是 v2、`interactive-prompts: off`、用文字範本問的題（選項超過 4 個或自由回答）。
`user_inbox: off` 時沒有待決清單，待辦分頁沒有題可答，也不寫。

---

## 為什麼「每次寫入就清」

`menu_open` 只出現在開選單前的那一次寫入；之後**任何一次**寫 `_tower-state.md`——選單回來後移除已回答的項目、處理 BAT 送來的文字回答、
開工、`*pause`……——都不寫這個鍵。下一次寫入本身又是另一個選單開之前的寫入時，寫的是新選單的 `ids`。

最初的提案是「選單回來那次寫入移除、開工時清掉殘留」。CT 放寬成「每次寫入都清」，理由是：

- **不必記得清。** 狀態檔每次寫入本來就整份重寫 frontmatter。只要「不是開選單前的那一次就不寫這個鍵」，殘留就不可能活過下一次寫入，
  不必另外在開工、收單、`*pause` 各處加清除步驟，也就沒有哪一處忘了清。
- **當掉或 compact 也一樣。** 塔台在選單開著時當掉，`menu_open` 會留在檔案裡；但塔台下一次寫檔（不管是開工還是別的事）就清掉了。
  在那之前，BAT 還有兩道保險：必須同時看到 `question` blocked，以及 `opened_at` 對得上。
- **不會誤清。** 選單開著時塔台不寫檔，所以不會在選單還開著時把欄位清掉。

依本文重寫摘要（Fast Path 恢復、`*rescan`）時，三個待辦清單原樣保留，但 `menu_open` **不保留**——它只描述「此刻開著的選單」，不是要保存的資料。

## 被關掉的選單：為什麼不重開

不分 Esc 是你按的、還是 BAT 為了送出待辦分頁的回答代按的，塔台處理都一樣：

1. 選單裡的每一題照留在 `awaiting_user`，不算回答、不算放棄，工單的 `waiting_user` 也留著（和 6.3.0 相同）。
2. 下一則回覆（BAT 送來的 `U-n：…`，或你自己打的字）照常處理回答、逐筆確認；同一個選單裡還沒答的題**不重開選單**，
   在確認行之後緊接著提醒一句（pre.2 寫明順序；沒有確認行時放在回覆開頭），例：「U-58 的選單已關閉，仍待決，可在待辦分頁或終端回答」，結尾照常重列 `⏸ 待你決定`。
   先確認、再提醒，你先看到塔台怎麼讀了你剛才的回答，和下一點又開新選單時的順序也一致。
3. 這一則回覆如果又**新增**了待決，新的那筆照常開選單，但選單**只放新的題**，不把剛才被關掉的題放回去。
   這時確認行照 6.3.0 的做法寫進第一題的題目開頭，上一點的提醒接在確認行之後。
4. 被關掉的題之後在任何地方回答都照常處理。想要它們再用選單問一次，說一聲「重問 U-58」，塔台才重開。

**為什麼。** 你在待辦分頁回答，代表你選擇在那裡作答。如果塔台每答一題就把剩下的題重開成選單，BAT 下一次又得代按 Esc，
你在待辦分頁每答一題，終端就閃一次選單——這正是 BAT 提案裡擔心的循環。剩下的題本來就還在待辦分頁、也還在每則回覆結尾的重列裡，不會被忘記。

**和 6.3.0 有什麼不同。** 規則其實沒變：6.3.0 的第 7 點也沒有要求重開舊題，「Esc 過後下一筆仍開選單」說的是**新的暫停**。
這次只是把它寫明，並把第 6 點「處理回答又開選單」的例子對齊（不再寫成「又有幾筆仍待決」就開選單）。

## 〈競態〉為什麼要改寫

6.3.0 的〈競態〉只寫了一種行為：選單開著時，待辦分頁送出的回答由 BAT 保留，選單關閉後才送到。BAT 支援代按 Esc 之後，這句就不完整了。
6.4.0 改寫成：

- 契約 v2 的 BAT 可能代按 Esc 關掉選單、再把回答送來（有 `menu` 時，只在回答的 `U-n` 在 `menu_open.ids` 裡）；塔台把這個 Esc 當成你按的 Esc。
- BAT 沒有代按時（回答不屬於這個選單、選單裡沒有 `U-n`），回答照舊保留到選單關閉。
- 權限、輸入對話框與 Worker 的通知照舊由 BAT 保留，不代按 Esc——那些不是待辦分頁的題，關掉它們會中斷別的事。
- 你已經在選單或終端回答過同一題時，晚到的那一行照「編號不存在或已結」處理，不會套用兩次。

## pre.2：為什麼文字範本的題要寫進題目

pre.1 驗收時有一回合是這樣：塔台同時要問三題，一題 2 個選項、一題 5 個選項、一題要你自由回答。原生選單一題最多 4 個選項、至少要 2 個，
所以只有第一題能開選單，另外兩題要用文字問。塔台開了那一題的選單，另外兩題只在選單前面說一句「改用文字問你」——
**終端從頭到尾沒有出現那兩題的選項與回答方式**。

原因和 6.3.0 把確認行寫進題目是同一個：回合的下一步是開選單時，模型常常不輸出選單前的文字，就算輸出了你也可能看不到；
**題目是開選單一定要寫、選單一開就顯示的內容**。所以 pre.2 規定：同一則回覆有的題開選單、有的題用文字時，文字的題寫進選單**第一題的題目**，
排在「剛才的回答：」確認行與被關選單的提醒之後、本題之前，每題一段，例：

```text
U-9（工單：—）下一階段先做哪個模組；選項 A 匯出／B 報表／C 權限／D 通知／E 稽核；回 U-9：<代號>。U-10（工單：—）新模組要叫什麼；回 U-10：<文字>。U-11（工單：—）<要決定什麼>
```

你在選單答 U-11，U-9、U-10 照題目寫的方式在終端或待辦分頁回答即可。文字的題超過 2 題、或一個題目塞不下時，那一則乾脆不開選單、全部用文字列出，
下一則再開——和 6.3.0「確認行超過 4 筆就不開選單」是同一種退路。`menu_open.ids` 只列開進選單的那一題，文字的題不在裡面：
它們不在選單裡，BAT 收到它們的回答時也就不必代按 Esc。

## pre.2：為什麼 `menu_open` 要緊接 `awaiting_user`

規則一直是「`menu_open` 和 `awaiting_user` 寫在開選單前的同一次寫入」。但塔台改檔用的是 Edit 工具，**一次 Edit 只能換掉一段連續的文字**。
pre.1 的範例把 `menu_open` 放在 `updated_at` 後面，離 `awaiting_user` 清單的結尾很遠；`awaiting_user` 原本已經有別的題、這次只是加一題時，
塔台照範例先在上面插 `menu_open`，再用另一個 Edit 在下面加新的題。兩個 Edit 之間存了一次檔，那一份的 `menu_open.ids` 指到一題還不在 `awaiting_user` 的題，
**自檢不合法**。

實際上沒有造成問題：那一份只存在幾秒、選單還沒開；BAT 讀到這種狀態時當作沒有 `menu_open`，回答照舊保留到選單關閉，不會誤按 Esc。
但這是「剛好沒事」，自檢報錯也會讓人以為檔案壞了。pre.2 改的是**寫法**，不是格式：

- **位置**：`menu_open` 寫在 `awaiting_user` 清單**正後方**（`user_actions`、`reminders` 之前）。新的題加在清單結尾，正好和 `menu_open` 相鄰，
  一個 Edit 就寫完——照範例寫最省事的做法，剛好也是正確的做法。
- **順序**（萬一還是分幾個 Edit）：`menu_open` 最後才寫，清除時最先拿掉。任何一次存檔後，`menu_open.ids` 都已經在 `awaiting_user` 裡。
- **讀者不看位置**：YAML 的鍵順序沒有意義，BAT 和自檢腳本都不依賴它；位置只是給塔台寫入用的，所以舊位置的檔照樣讀得懂，不必改。

為什麼不改用一支腳本一次寫入、或把自檢降成提示？腳本要另寫、要測、模型還得記得改用它，為一個實際風險為零的中間狀態不值得；
自檢則是在全部 Edit 之後才跑，那時還不合法就是真的錯了（BAT 會不理會 `menu_open`），所以照樣擋。

## 為什麼還是契約 2：能力旗標 `menu`

`menu_open` 是新增的選填欄位，沒有改掉任何既有欄位的名稱、型別或語意，所以 `bat_contract` 仍是 2、`summary_version` 不升（和 6.2.0 的 `dismiss`、6.3.0 的 `multi` 同一個做法）。
但 BAT 需要知道一件事：**「狀態檔裡沒有 `menu_open`」到底是「沒有開著含 `U-n` 的選單」，還是「這個塔台根本不會寫 `menu_open`」**。

所以 CT 6.4.0 起每次寫狀態檔都寫 `inbox_features: ["recommended", "dismiss", "multi", "menu"]`。有 `menu`，BAT 才信任「沒有 `menu_open` ＝ 沒有選單」；
沒有 `menu`（CT 6.3.x 以前），BAT 不理會 `menu_open`，照它自己的預設處理。能力寫在狀態檔、不加進 `--set-role`，開工宣告與降級提示都不變。

## 常見誤解

- **「`menu_open` 是給我看的待辦」**：不是。它只是給 BAT 判斷「這個回答屬不屬於開著的選單」，待辦還是看 `awaiting_user`。
- **「選單被 BAT 關掉，剩下的題就不見了」**：沒有。它們照留在待辦分頁，每則回覆結尾也照常重列；只是不再自動開成選單。
- **「被關掉之後就永遠只能打字」**：不是。新的暫停仍開選單；舊題要再用選單問，說「重問 U-n」。
- **「開工時要另外清 `menu_open`」**：不用。任何一次寫入都不寫這個鍵，開工那次寫入就清掉了。
- **「需求對齊的選單開著時，待辦分頁的回答也會關掉它」**：不會。需求對齊的選單沒有 `U-n`，塔台不寫 `menu_open`，BAT 照舊保留回答。
- **「這需要契約 3」**：不需要。新增欄位加能力旗標，契約仍是 2。
- **「pre.2 改了 `menu_open` 的位置，舊的狀態檔要改」**：不用。讀者不看鍵的位置，位置只是給塔台寫入用的；塔台下一次寫入就照新位置。
- **「用文字問的題不在選單裡，就不用在終端看了」**：不是。pre.2 起它們寫在選單第一題的題目裡，照題目寫的方式回答即可。
- **「選單交接還是預覽、還沒在實機跑過」**：不是。6.4.0 起是正式版，pre.1 與 pre.2 的修正都已在 BAT 0.8.1-pre.4 上實機驗證；還沒驗的路徑見下方〈已知未驗〉。

## 已知未驗

見 CT `CHANGELOG.md` `[6.4.0]` § Known unverified（預覽期間的紀錄在 `[6.4.0-pre.2]`、`[6.4.0-pre.1]`）。

**已驗證**（6.4.0-pre.1 與 6.4.0-pre.2 在 BAT 0.8.1-pre.4 上的雙方實機驗收）：

- BAT 依 `menu_open.ids` 代按 Esc、以 `opened_at` 防殘留
- 塔台只在開選單前那一次寫入寫 `menu_open`、之後的寫入都不寫；Esc 殘留與人為注入的殘留被下一次寫入清掉
- 被關選單不重開、提醒、新待決只放新題、「重問 U-n」才重開；晚到的重複回答照「編號不存在或已結」處理
- 需求對齊與 `interactive-prompts: off` 不寫 `menu_open`；CT 6.4.0 搭舊 BAT 0.8.1-pre.3、CT 6.3.0 搭新 BAT 都沒有回歸
- pre.2 的兩個修正：文字問的題寫進選單第一題的題目；`menu_open` 緊接 `awaiting_user`、每一份中間存檔都通過自檢

**仍未驗**（與 CT `CHANGELOG.md` `[6.4.0]` 相同；`[6.3.0]` 以前列的項目不變）：

1. Codex 塔台：沒有選單，不寫 `menu_open`，所有題走文字範本；沒有 Codex 環境，未實機確認
2. BAT 遇到權限詢問或 MCP 要求輸入（`permission`／`elicitation`）的暫停時，照舊保留回答、不代按 Esc：驗收環境略過權限詢問、也沒有會要求輸入的 MCP，沒有觸發；以 BAT 文件為準
3. 混用選單與文字問的題的幾個分支：文字題超過 2 題或寫不下時「這一則不開選單」的退路、文字題是多選題時的「可複選」寫法、
   同一則回覆同時有「剛才的回答：」確認行時的完整順序（確認行 → 提醒 → 文字題 → 本題）。驗收只有 2 題文字題、沒有確認行，都沒有觸發
4. 分幾次寫時「`menu_open` 最後寫、最先清」的順序：驗收中寫入與清除都是一次完成；被回答的題不是清單最後一筆、必須分開寫的情況沒有觀察到
   （就算順序寫反，BAT 也只是當作沒有 `menu_open`、不會誤按 Esc，自檢會擋下）
5. 下一則回覆不開新選單時，提醒緊接在確認行之後：補跑沒有這個情況（第一輪兩種順序都出現過，都沒有違反當時的條文）
6. Worker 提問升級給你的選單（`worker-question`），以及選單開著時從待辦分頁回答 `A-n`（保留到選單關閉）：不在驗收清單，條文和塔台提問的選單相同
7. 重複的鍵（`duplicate-key`）：檢查腳本有樣本測試，並對本專案的工單目錄（561 份 frontmatter）新舊腳本比對、沒有新增誤報；BAT 也用樣本確認過整份讀不到。
   驗收中塔台沒有實際寫出重複的鍵，所以「塔台寫錯時自檢擋下」這條路徑沒有實機發生；BAT 端行為以 BAT 文件為準
